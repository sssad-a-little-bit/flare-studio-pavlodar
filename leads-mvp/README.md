# Flare Studio: локальная база лидов

Работающий небольшой MVP для поиска и ручной квалификации местных бизнесов Павлодара и Экибастуза. Python 3.11+, SQLite, миграции SQL, CLI на русском, импорт и экспорт CSV/XLSX. Сервер, веб-интерфейс, платные сервисы и внешняя публикация не нужны. Система сама не звонит, не пишет сообщения и не запускает задания по расписанию.

**Подтверждённый действующий официальный сайт исключает бизнес из активных лидов.** Неоднозначный или непроверенный сайт блокирует готовность к звонку. «Не найден при проверке» означает ограниченный результат конкретной проверки: это не доказательство отсутствия сайта и не признак желания купить разработку.

## Установка и локальный запуск

В корне проекта, Linux/macOS:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e '.[test]'
cp .env.example .env
set -a
. ./.env
set +a
flare init
flare --help
```

В Windows можно использовать Python 3.11+, `.venv\Scripts\Activate.ps1` и задать переменные через `$env:FLARE_DB = 'data/flare.sqlite3'`. `.env` автоматически не читается: загрузите значения в окружение своего терминала. Файл должен содержать только доверенные назначения переменных; команда `. ./.env` выполняет его как shell-код.

По умолчанию база создаётся в `data/flare.sqlite3`. Глобальный параметр `--db` ставится **перед** командой:

```bash
flare --db data/review.sqlite3 init
python -m flare --db data/review.sqlite3 list
```

Миграции из `flare/migrations/` применяются автоматически перед каждой командой; `init` позволяет выполнить их отдельно. Применённые версии записываются в `schema_migrations`. Не удаляйте SQLite-файл для обновления программы: в нём находятся история и ограничения контакта. Перед обновлением сохраняйте резервную копию закрытой базы.

## Источники и первый сбор

Реализован бесплатный публичный источник **OpenStreetMap через Overpass API**. Ключ не требуется. Это исходные наблюдения, которые необходимо проверить, а не готовая база покупателей:

```bash
flare collect --city Павлодар --category кафе --sources osm --limit 5
flare list --city Павлодар
flare attempts
```

Поддерживаются Павлодар и Экибастуз; категории: `кафе`, `ресторан`, `парикмахерская`, `салон красоты`, `стоматология`, `автосервис`, `отель`, `магазин`, `фитнес`. География ограничена приблизительными прямоугольниками; адрес и филиал требуют проверки. `--limit` принимает 1–100.

Список `--sources` может содержать `osm,2gis,yandex,instagram`. Для трёх последних MVP сохраняет статус недоступности и причину, продолжая остальные источники:

```bash
flare collect --city Экибастуз --category автосервис --sources 2gis,osm,yandex,instagram --limit 5
flare attempts
```

* 2GIS: нет подключённого адаптера; необходимы ключ, подходящие права хранения и отдельное согласование контактных полей. Добавление ключа само по себе сбор не включает.
* Яндекс: стандартные условия Organization Search API запрещают сохранение полученных данных, поэтому такой сбор отключён.
* Instagram: разрешённый универсальный поиск местных бизнес-профилей не подтверждён; автоматического сборщика нет.
* Поисковики: ручной поиск и сохранение кратких доказательств. Автоматического скрейпера выдачи нет.

Официальные документы, проверенные ограничения, коды ошибок и атрибуция приведены в [docs/SOURCES.md](docs/SOURCES.md). Альтернатива недоступным источникам — собственная CRM или другой список, который разрешено хранить и обрабатывать.

При проверке подключения 7 ноября 2026 года запрос OSM «кафе, Павлодар, лимит 5» вернул пять реальных объектов: без телефонных тегов, с одним кандидатом сайта. Эта выборка не даёт готовых к звонку лидов. В неё не добавлялись синтетические компании; публичный сервер может быть недоступен при следующем запуске.

## Импорт CSV/XLSX

Используйте [examples/import-template.csv](examples/import-template.csv): это только заголовки, без выдуманных компаний. Заполните его своими разрешёнными данными или сопоставьте столбцы существующей CRM с приведёнными ниже именами. Обязательны `name`, `city`, `category`; при отсутствии доказательств не ставьте признаки подтверждения.

```bash
cp examples/import-template.csv leads.csv
# Заполните leads.csv своими данными, затем:
flare import leads.csv --source my-crm
flare import leads.xlsx --source my-crm
```

Сохраняйте одно и то же значение `--source` для одной CRM и устойчивый `source_external_id` для одной компании/филиала. Повторный импорт обновит известную запись, сохранив историю и ограничения. Новое имя или появление сайта не создают дубль при сохранении устойчивого идентификатора. При отсутствии такого ID особенно важны точный адрес и деловой телефон. Не используйте один внешний ID для всей сети.

CSV: UTF-8, допустим BOM; разделитель запятая, точка с запятой или табуляция определяется автоматически. XLSX: первый активный лист, заголовки в первой строке, формулы запрещены. Телефоны, WhatsApp и деловые контакты в XLSX должны быть **текстовыми** ячейками; числовые ячейки отвергаются, чтобы не скрыть повреждение номера. Неизвестные или повторяющиеся заголовки требуют исправления до импорта. Предел — 25 МБ и 50 000 строк на файл.

Отчёт содержит `processed`, `created`, `updated`, `errors` с номером строки и причиной. Ошибка одной записи откатывает только эту строку; остальные сохраняются. При ошибке чтения CSV сообщается место остановки; ранее обработанные строки отражены в отчёте. Исправленный файл можно импортировать повторно. Отсутствующее логическое значение не означает подтверждение; допустимы `true/false`, `1/0`, `да/нет`. Десятичный разделитель `confidence` — точка. Даты — ISO 8601, например `2026-11-07T08:00:00+00:00`; будущие даты не принимаются.

| Поля | Значение и правила |
|---|---|
| `source_external_id` | Устойчивый ID компании/филиала внутри указанного `--source`. |
| `name`, `category`, `city`, `address` | Название, категория, город, адрес. Первые три обязательны; без адреса запись не готова к первому звонку. |
| `phone`, `phone_type`, `phone_verified` | Телефон, тип `business` / `owner` / `manager`, явное подтверждение. Номера Казахстана нормализуются в `+7…`; российские номера не принимаются как казахстанские. Для подтверждения нужен `source_url`. Общий телефон не становится контактом владельца. |
| `whatsapp`, `whatsapp_verified` | Только явно подтверждённый WhatsApp. Наличие мобильного номера само по себе не подтверждает WhatsApp. |
| `email`, `profile_url` | Опубликованный деловой email и бизнес-профиль. Профиль/каталог не считается официальным сайтом. |
| `contact_name`, `contact_role`, `contact_business`, `contact_verified` | Подтверждённые имя, роль и деловой телефон/email владельца или ответственного. Нужны все поля, подтверждение и `source_url`; иначе оставьте их пустыми. |
| `source_url`, `observed_at`, `confidence` | Публичный URL происхождения, дата получения факта, уверенность 0–1. Если дата/уверенность отсутствуют, импорт фиксирует время импорта и 0.5: для старых CRM укажите фактическую дату, чтобы не приписывать свежесть. Без публичного URL сохраняется пометка ручного импорта, а не внешнее доказательство. |
| `website` | Кандидат официального сайта; одна ссылка не подтверждает его принадлежность. |
| `website_status` | `unchecked` — не проверено; `ambiguous` — принадлежность неоднозначна; `not_found` — не найден при конкретной проверке; `found` — подтверждён действующий официальный сайт. |
| `website_checked_at`, `website_check_source`, `website_evidence`, `website_check_methods` | Дата, название способа/источника, краткие основания и методы. Для проверенного статуса нужны эти данные и `source_url`. Для `found` / `not_found` — минимум два метода из `search`, `profile`, `contacts`; в CSV/XLSX разделяйте их **точкой с запятой**. |
| `signal_type`, `signal_quote`, `signal_reason`, `signal_date`, `signal_url` | Два типа сигнала описаны ниже. Цитаты/причины — максимум 600 символов. |
| `stage` | Одна из стадий ниже. Готовность к первому звонку всё равно вычисляется по правилам допуска. |
| `do_not_contact` | Отдельный устойчивый запрет контакта. `false` при повторном импорте не снимает ранее установленный запрет. |
| `exclusion_reason` | Краткая причина исключения, максимум 600 символов; не исчезает от обычного обновления. |

При обновлении сохраняются прежние наблюдения и доказательства. Дедупликация использует ID источника, нормализованные телефон/профиль вместе с адресом и городом, название вместе с местоположением. Один общий телефон или сайт сети не объединяет разные адреса. Конфликт разных устойчивых идентификаторов отклоняется и требует ручного разрешения. При отсутствии стабильного ID и адреса идентичность слабая: переименование такой записи может потребовать ручного исправления через `edit`.

## Проверка официального сайта и карточка

```bash
flare list
flare show 1
flare show 1 --json  # полная история в машиночитаемом виде
```

Число `1` в примерах — ID из вашего вывода `list`. Карточка показывает текущие телефоны и ответственных, доказательства и ссылки, наблюдения и историю, статус сайта, сигналы, качество данных, факторы приоритета, блокирующие причины и следующий шаг.

Вручную выполните поиск по названию + городу + телефону, проверьте ссылки из бизнес-профиля/карточки и сопоставьте опубликованные контакты сайта. Сохраните конкретные основания и дату. Если в записи есть кандидат, доступна ограниченная HTTP-проверка:

```bash
flare probe-site 1
```

Она проверяет публичную страницу и совпадения названия/города/телефона, учитывает robots.txt, таймауты и ограничения ответа. Это вспомогательные наблюдения: результат **не** устанавливает `found` автоматически и оставляет ручную проверку. Недоступная страница не превращается в доказательство отсутствия сайта. Полное содержимое страницы в базе не сохраняется.

Запишите только реально выполненную проверку. В следующих командах замените переменные своими доказательствами и ID; `--checked-at` укажите отдельно, если проверка выполнена раньше:

```bash
# EVIDENCE_URL — публичная ссылка; CHECK_NOTE — краткие фактические основания.
flare verify-site 1 --status not_found --url "$EVIDENCE_URL" --evidence "$CHECK_NOTE" --methods search,profile
flare verify-site 1 --status ambiguous --website "$CANDIDATE_URL" --url "$EVIDENCE_URL" --evidence "$CHECK_NOTE" --methods contacts
flare verify-site 1 --status found --website "$OFFICIAL_URL" --url "$EVIDENCE_URL" --evidence "$CHECK_NOTE" --methods profile,contacts
```

Здесь методы разделены **запятой**, в отличие от столбца импорта. Для `found` оператор должен подтвердить действующий официальный сайт, а не каталог или соцсеть. Установленный `found` и причина исключения устойчивы: обычные импорт/сбор/редактирование их не отменяют. Если старое исключение было ошибочным, автоматического снятия нет — потребуется отдельное ручное исправление данных с сохранением обоснования.

Ручные исправления остальных данных принимаются из JSON-объекта с полями шаблона импорта:

```bash
flare edit 1 --file correction.json
```

Например, для исправления адреса создайте объект с полем `address`; для подтверждения телефона добавьте сам `phone`, `phone_verified: true`, URL источника и дату проверки. Не ставьте `true` без фактической проверки. Исправление по ID позволяет изменить название/адрес без создания новой карточки. Пустое значение при обновлении не удаляет старые факты; удаление контакта выполняется отдельной командой.

## Интерес, качество данных и очередь звонков

`confirmed_demand` — подтверждённый спрос. Для публичного сообщения обязательны конкретная цитата `signal_quote`, ссылка `signal_url` и дата `signal_date`. Альтернатива — пользователь записывает интерес после состоявшегося разговора командой `contact --outcome заинтересован`.

`likely_benefit` — гипотеза пользы сайта, например удобство бронирования или каталога услуг. Обязательны `signal_reason` и `signal_date`. Такая гипотеза не объявляется желанием купить сайт, подтверждённым бюджетом или финансовым состоянием. Ни один тип сигнала автоматически не выводится из отсутствующего тега `website`.

По умолчанию приоритет складывается из: актуальный подтверждённый спрос **40**, актуальная обоснованная польза **20**, свежий подтверждённый деловой телефон **25**, свежие бизнес-данные **15**. В карточке показан вклад каждого фактора. Это настраиваемый рейтинг очередности, **не статистическая вероятность покупки**. `data_quality` отдельно отражает уверенность последнего наблюдения бизнес-данных в шкале 0–100; это не независимая внешняя сертификация качества.

Бизнес готов к **первому ручному звонку**, только когда одновременно:

1. Нет запрета контакта, причины исключения и ранее обработанной стадии.
2. Сайт `not_found` по свежей проверке; нет нерешённого кандидата или неоднозначности.
3. Установлены адрес/филиал и свежий подтверждённый деловой телефон.
4. Бизнес-данные свежие, есть актуальный спрос или обоснованная гипотеза пользы.

```bash
flare list --ready --city Павлодар
flare list --stage 'требует проверки'
flare export exports/call-queue.csv --ready --city Павлодар
flare export exports/call-queue.xlsx --ready
```

Готовность и стадия пересчитываются при чтении, поэтому старые записи не остаются в очереди только из-за прежнего статуса. Высокий приоритет не отменяет блокирующие причины. Повторный сбор/импорт не возвращает обработанные компании в очередь первого контакта.

Стадии: `новый`, `требует проверки`, `готов к звонку`, `связались`, `заинтересован`, `отказ`, `перезвонить`, `клиент`, `исключён`. Первые стадии отражают результат текущей квалификации; фактический контакт и результаты фиксирует оператор:

```bash
flare contact 1 --outcome связались --kind call --note 'Краткая фактическая заметка после ручного звонка'
flare contact 1 --outcome заинтересован --kind meeting --note 'Подтверждённый итог состоявшейся встречи'
flare contact 1 --outcome перезвонить --kind note --note 'Согласованный следующий шаг'
flare list --stage перезвонить
flare block 1 --reason 'Фактическая причина запрета повторного контакта'
```

Команда `contact` только сохраняет уже состоявшееся взаимодействие/заметку, а не выполняет звонок или отправку. Примеры заметок замените фактическими итогами. Не отмечайте интерес при отсутствии разговора. `перезвонить` не создаёт автоматического напоминания; оператор ведёт дальнейшую работу вручную. Запрет контакта хранится отдельно от стадии и не имеет команды автоматического сброса.

## Экспорт, исправление и удаление

```bash
flare export exports/all.csv
flare export exports/all.xlsx --city Экибастуз
flare delete-contact 3
flare delete 1
```

`delete-contact` принимает **ID контакта из карточки**, удаляет текущий контакт, но сохраняет старое наблюдение в истории. Для удаления карточки вместе с контактами, доказательствами, наблюдениями и взаимодействиями используйте `delete` с ID бизнеса. Удалённые ранее обработанные/запрещённые записи оставляют SHA-256 устойчивых идентификаторов и признак запрета: повторный импорт совпавшего бизнеса будет исключён. Хеширование уменьшает объём сохраняемых данных, но не является гарантией анонимности; не публикуйте базу и файлы подавления. При полностью изменившихся идентификаторах связать удалённую запись с новой может быть невозможно.

Экспорт содержит отдельные плоские столбцы телефонов, WhatsApp, email, ответственного, пользы сайта, интереса и приоритета. Полные контакты, доказательства и история дополнительно сохранены в JSON-ячейках. Это **отчёт, а не файл для прямого обратного импорта**: для импорта сопоставьте нужные поля с шаблоном и исключите дополнительные отчётные столбцы. Не используйте выгрузку как способ сбросить стадии или запреты. Строки, которые табличный редактор мог бы выполнить как формулу, получают защитный апостроф, включая телефоны с `+`. Если JSON-история превышает предел ячейки XLSX 32 767 символов, выберите CSV: данные молча не обрезаются.

База, импорты, выгрузки и заметки могут содержать персональные данные. Храните их локально с доступом только уполномоченным сотрудникам, не коммитьте в репозиторий и самостоятельно управляйте сроками хранения/резервными копиями. Сохраняйте только явно опубликованные деловые контакты и краткие выдержки. Не добавляйте личные контакты без делового назначения, догадки о владельце, закрытые профили и полные страницы. Для данных OSM сохраняйте атрибуцию и ссылки согласно [docs/SOURCES.md](docs/SOURCES.md).

## Переменные окружения

Все настройки читаются из окружения. В MVP нет обязательных секретов; `.env.example` не содержит ключей. При дальнейшем подключении разрешённого API ключи следует передавать только через окружение, не CSV, аргументы команд или журналы.

| Переменная | По умолчанию / назначение |
|---|---|
| `FLARE_DB` | `data/flare.sqlite3`; переопределяется `--db`. |
| `FLARE_DATA_FRESH_DAYS` | `90`: свежесть бизнес-данных, подтверждённого телефона и проверки сайта. |
| `FLARE_DEMAND_FRESH_DAYS` | `30`: актуальность подтверждённого спроса. |
| `FLARE_BENEFIT_FRESH_DAYS` | `180`: актуальность гипотезы пользы. |
| `FLARE_SCORE_DEMAND` | `40`: вес актуального подтверждённого спроса. |
| `FLARE_SCORE_BENEFIT` | `20`: вес актуальной пользы сайта. |
| `FLARE_SCORE_CONTACT` | `25`: вес свежего подтверждённого делового телефона. |
| `FLARE_SCORE_FRESHNESS` | `15`: вес свежих бизнес-данных. |
| `FLARE_HTTP_TIMEOUT` | В `.env.example` — `15` секунд; сборщик Overpass без переменной использует 30, HTTP-проверка сайта — 15. |
| `FLARE_REQUEST_INTERVAL` | В `.env.example` — `2` секунды; Overpass без переменной — 3, проверка сайта — 2. |
| `FLARE_HTTP_RETRIES` | В `.env.example` — `1`, применяется к HTTP-проверке сайта с верхним пределом 2 повтора. Overpass независимо ограничен одним повтором. |
| `FLARE_OVERPASS_URL` | `https://overpass-api.de/api/interpreter`; необязательная замена на разрешённый HTTPS endpoint Overpass. |

Пороги и веса — целые неотрицательные числа. Сетевые параметры ограничены в коде; 401/403, CAPTCHA и ограничения доступа не обходятся. Повторы конечны, ошибки источников фиксируются безопасными кодами. `collect` и импорт могут завершиться частично успешно: внимательно читайте отчёт и `attempts`. Коды CLI: `0` — успех, `2` — ошибки строк/частично недоступные источники, `1` — ошибка ввода, файла или базы.

## Структура и проверка

`businesses` хранит текущую карточку; `contacts` — отдельные контакты; `sources` и `evidence` — происхождение, время, короткую выдержку и уверенность; `observations` — неизменяемые старые факты и сигналы; `collection_attempts` — попытки сбора; `interactions` — ручные контакты и заметки. `identities` обеспечивает осторожную дедупликацию, `suppressions` — сохранение ограничений после удаления. Это одна локальная SQLite-база, без внешних служб.

```bash
python -m pytest -q
flare --db /tmp/flare-check.sqlite3 init
flare --db /tmp/flare-check.sqlite3 import examples/import-template.csv --source template-check
flare --db /tmp/flare-check.sqlite3 list --ready
```

Пустой шаблон импортирует ноль строк — это проверка формата, а не пример реального сбора. Тесты используют явно помеченные синтетические данные в `tests/`, отдельные временные базы и подменённые сетевые ответы. Они проверяют дедупликацию и идемпотентность, устойчивые исключения/запреты, отличие спроса от гипотезы, недоступность источника без остановки других, импорт и защиту выгрузок. Реальный сетевой запуск выполняется отдельно командой `collect`; его результат не подменяется тестовыми компаниями.

Остаются ручными проверка официальности и работоспособности сайта, опубликованного делового назначения телефона, личности ответственного, актуальности спроса и прав использования источника, разрешение конфликтов идентичности и сами контакты. Система помогает сохранить основания решений и соблюсти очередь, а не устанавливает эти факты по догадкам.
